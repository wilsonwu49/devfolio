LiDAR autonomous navigation robot

Type
Personal project, built alone
Hardware
RPLIDAR, STM32L432KC, Raspberry Pi 4
Status
Simulation only

I started this robot to get hands-on experience with LiDAR, and it grew into my main project as I taught myself state estimation and control through study guides I wrote along the way. The software runs multi-rate across an STM32 and a Raspberry Pi using plain Python threading instead of ROS 2, and it does LiDAR odometry rather than full SLAM, so there is no loop closure.

A rough pipeline with a rigorous safety filter is a paper. A beautifully integrated pipeline with no safety filter is a robot demo.

What works, in simulation

  • ICP that knows when it is lost. It returns a covariance from σ²(AᵀWA)⁻¹, gated on condition number and inlier count. In a featureless corridor the eigenvalue ratio along the unobservable axis reaches about 10¹⁷, so the match gets rejected instead of feeding the filter a confident wrong answer.
  • Error-state EKF. 15 states, Hamilton quaternion attitude, Joseph-form covariance, chi-squared NIS gating on every update. Process noise is seeded from the BMI270 datasheet. Jacobians check out against finite differences.
  • Estimator plus ICP. A 200-step run with prediction, encoder updates and ICP updates ends with 3.3 mm position error and 3.4 mrad yaw error.
  • Occupancy grid. Log-odds with clamping and Bresenham ray tracing. On a 360° synthetic fan against a straight wall, all ~90 wall-hitting beams land in exactly one grid column. Free space is only carved out to a trusted clearing distance, since a missing return may be a dark surface.
  • Planning and control. A* planner, pure pursuit tracking, and a CBF-QP safety filter on the command.

A negative result: I designed the safety margin to grow with √tr(P), the size of the filter's covariance, so that a less certain robot would keep more distance from obstacles, and it turned out to have the same structure as the tr(Σ) penalty in Prof. Cosner's ORIO paper, which I read afterward. In simulation it did not help, and it may have made things worse.

Limits

Nothing has run on hardware yet, since the main event loop and hardware bring-up aren't done and the STM32 firmware for the encoders, IMU, motor PWM and the link to the Pi is still unwritten. Every test so far uses synthetic data generated under the estimator's own assumptions, which means the noise is Gaussian because I drew it that way, and characterizing the real IMU bias will need an Allan variance log I haven't taken. The first RPLIDAR is also blocked by a faulty USB adapter, so I've ordered a replacement A1M8.

Next semester

I'm planning to open source the code and run it as a build project with the Tufts Robotics Club, where I can teach members the estimation and safe-control parts.
